# 问题分析与解决规范

> 来源：2026-08-30 用户多次纠正后确立。在状态机 + 战斗系统打磨期间，AI 多次出现"看数值不看机制 / 砍功能当方案 / 推荐与需求相反的方案"等错误，整理成规范。

## 一、查证问题：先看机制，再看数值

### ❌ 错误做法
- 只盯**数值偏差**（如"重剑手得 9 / 勇者得 12"），不分析**机制是否符合预期**
- 看到数值匹配就认定"机制对"，看到数值偏差就认定"有 bug"

### ✅ 正确做法
- **先看卡牌描述**（卡牌表格里的"效果"列是权威源），**弄清期望机制**
- **再查实现机制**（代码层做了什么）
- **最后对比**（期望 vs 实现）— 数值偏差 = 机制不对

### 案例：大地护盾
- **期望机制**：每个友军**自己**走标准 Shield 流程（3 次 `Defend + extraShield`）
- **当前机制**：把**施法者累积**复制给每个友军，友军再叠加自己 `Defend` —— 错
- 数值"9 / 12"在当前错机制下**正好**匹配，不是 bug，但**机制不对**

## 二、解决问题：绝不砍功能

### ❌ 错误做法
- 为了快速修复，**删除**某项功能 / 检查 / 状态记录
- 例如：问题 7 紧咬不放 — 推荐"移除 OwnerUnit 检查"——这砍掉了"对特定玩家反击"的语义

### ✅ 正确做法
- **保留全部功能**，通过正确实现让功能工作
- 必要时**扩展数据结构**（加字段）+ **改调用方**（传新参数）
- 例如：问题 7 — 扩展 `AddOrUpdateState` 接受 `ownerUnit` 参数 + `StateRuntimeData` 持久化 + `ApplyAddStateEffect` 传 `source` —— 功能完整保留

## 三、查随机 vs 选牌

### ❌ 错误做法
- "只有 1 张符合要求" 就认为**自动随机**可以接受
- "SelectHandCards 和 RandomHandCards 行为相同"是**错的**

### ✅ 正确做法
- **没有强调随机的卡牌 = 选牌**（必须弹选牌 UI）
- "SelectHandCards" = 用户从手牌中**选** count 张
- "RandomHandCards" = 系统**随机抽** count 张
- 卡牌描述中**显式说**"随机"才用 RandomHandCards

## 四、查资源给护盾：基础值 vs Shield 公式

### ❌ 错误做法
- 给"下回合开始时获得 N 资源"时，调 `EffectSystem.ApplyShield(unit, [N])` — 公式 `Defend + N` 叠加了 Defend

### ✅ 正确做法
- 资源给护盾应该**直接** `unit.Shield += amount`（**不**叠加 Defend）
- 资源量 = 卡牌描述"额外获得 N 点格挡" 中的 N（**纯基础值**）
- 例：预判卡"下回合开始时额外获得 1 点格挡"——下回合给 1 护盾（**不**叠加 Defend）

## 五、查 OnTurnStart：资源给 vs 状态清除顺序

### ❌ 错误做法
- 调点顺序错误：先 `StateDecayProcessor` 清除 → 再 `OnTurnStart` 给资源（资源**永远给不到**）

### ✅ 正确做法
- **严格顺序**：先 `StateSystem.OnTurnStart(unit)`（给资源） → 再 `StateDecayProcessor.ProcessDecayAtTiming(unit, OnTurnStart)`（清除）
- 同理：先 `OnTurnStart` 给资源 → 再 `StateDecayProcessor` 处理 `OnTurnStart` 时机

## 六、查状态机制：ownerUnit 等关键字段

### ❌ 错误做法
- 把"没传某字段"当成"字段不需要"——**砍功能**
- 例如：问题 7 — `ApplyAddStateEffect` 调 `AddOrUpdateState` 没传 ownerUnit —— 应**保留** ownerUnit 语义，扩展 `AddOrUpdateState` 接收

### ✅ 正确做法
- 状态机制语义要求**保留**——通过正确的数据流实现
- 关键字段：`ownerUnit`（施加者）/ `stateCardUniqueInGameId`（来源状态牌）等

## 七、查 Tween 动画时长 vs 持续时间

### ❌ 错误做法
- 把"0.15s"当成"高亮持续 0.15s"——**错的**
- 0.15s 是 tween **过渡时长**（动画过程），tween **完成后** Scale **保持**在目标值

### ✅ 正确做法
- tween 0.15s = "从 1.0 放大到 1.15 用 0.15 秒"
- tween 完成后 Scale **保持**在 1.15，直到下次 on=false
- 真正"高亮持续时间" = 从 on=true 到下次 on=false 的时间
- 间隔 0.5s = 怪物结算之间的等待时间，**与 tween 无关**

## 八、查数值：实际单位数值

### ❌ 错误做法
- 凭印象给数值（如"勇者 Defend=4"）
- 不查 DataBase/Unit/Character.csv

### ✅ 正确做法
- 涉及具体单位数值（Defend / HP / Attack）必须**查 CSV**确认
- 例：勇者 Defend 实际是 3（DataBase/Unit/Character.csv 确认），不是 4

## 九、查回应：用大白话，禁堆变量名

### ❌ 错误做法
- 回应里堆 `FieldName` / `MethodName` / `EffectType.X` 等变量名
- 用户看不懂

### ✅ 正确做法
- 用**人话**描述问题：机制是什么、现象是什么、为什么错
- 必要时引用代码（但要解释），不假设用户能读代码

## 十、查回应：具体到"机制级别"，不要"砍功能换通过"

### ❌ 错误做法
- 看到"OwnerUnit 是 null" → "删 OwnerUnit 检查"——**砍功能**
- 看到"日志不完整" → "改时序"——**动时序**

### ✅ 正确做法
- 看到"OwnerUnit 是 null" → 查**调用链**找"为什么没传"——**修调用方**
- 看到"日志不完整" → **加日志**（不动执行顺序）
- 看到"机制不对" → 修**机制**（不是绕开）

## 十一、查状态：先 read 再 write，不要瞎覆盖

### ❌ 错误做法
- 用方案覆盖**用户维护的文件**（如 `待做事项.md`），丢失用户已写内容

### ✅ 正确做法
- 用 read 工具**先读**当前文件内容
- 用 write 时**保留**已有内容 + 追加新内容
- 用户明确"我的问题在 X 文件里"——必须**先 read X**确认

## 十二、查问题根因：必须走完函数执行顺序，不靠猜

### ❌ 错误做法
- 看到调点存在就推断"应该工作"
- 看到"函数内部有给资源代码"就推断"已触发"
- 不**完整**走完函数体（含 if 分支、循环顺序、`toRemove` 末尾统一 Remove），反复猜"可能是 X 可能是 Y"
- 用户多次纠正后仍继续猜

### ✅ 正确做法
- 走完 `OnTurnStart` 类函数的**完整执行顺序**：循环 1 → 循环 2 → 末尾 Remove
- 模拟**每一步**的 `unit.States` 状态变化
- 看**同一函数**内多个分支对**同一状态**的操作顺序
- 查证：状态 A 被 line X 移除 → line Y 查 `TryGetStateStacks(A)` 会失败 → line Y 永远不执行
- **实际**走一遍才能定位

### 案例：问题 6（预判下回合给护盾失败）—— 我反复猜了 3 次
- **第 1 次（错）**："实际触发给资源，只是被问题 1 bug 影响多给"——没走 `OnTurnStart` 内部顺序
- **第 2 次（错）**："总护盾数 8 对"——只看总数，没看分配
- **第 3 次（错）**："下回合开始时给资源，受问题 1 bug"——仍靠猜
- **第 4 次（对）**：走完 `OnTurnStart` 函数体 → 发现**先**衰减 TurnStartEffect（`TurnStartDecayAmount=1`）→ `toRemove.Add` → **再**查 `TryGetStateStacks` → Stacks=0 → **永远不**给资源

**教训**：看到"调点存在 + 函数有逻辑" ≠ "实际工作"。必须**模拟执行顺序**才能定位。

## 十三、记录引用：禁 #1 #2，必须完整

### ❌ 错误做法
- 用 `#1 #2 #3` 指代问题 / 方案 / 任务
- 不写文件来源（"问题 1 在哪个文件"）
- 不写问题梗概（"问题 1 是关于什么的"）
- 上下文不连贯：别人（甚至自己）隔几天回来看，**看不懂** `#1` 是什么

### ✅ 正确做法
- 每次引用必须**完整三要素**：
  1. **文件来源**（哪个文件 / 哪个函数 / 哪行）
  2. **问题 / 任务梗概**（一句话说明是什么）
  3. **状态**（已查证 / 实施中 / 待批 / 已完成）
- 写完整句子或表格行，不用 `#1` 缩写
- 表格列名要具体（如"大地护盾（`Scripts/UI/CardBattleScene.cs:ShowStateTooltip`）"），不用"问题 1"

### 案例：错误 vs 正确

| 错误 | 正确 |
|------|------|
| `#1 修复了 #3 影响了 #5` | "大地护盾（`Scripts/UI/CardBattleScene.cs:ShowStateTooltip`）修复了 调点顺序；这影响了 燃血（`DataBase/Card/重剑手Card.csv:31002005`）的状态机；还需要 紧咬不放（`Scripts/System/StateSystem.cs:OnMonsterAttackPlayer`）修复" |
| "`#1` 已查证根因" | "大地护盾机制不对（`Scripts/Entity/Card/Card.cs:ApplyMirrorShieldToAlliesEffect`）：勇者 Defend=3 + 累积 9 = 12 护盾（错误，应为各自 9 护盾）；状态：已查证根因" |
| "按 #1 实施" | "按方案 `README/施工文档/2026/2026.08/P0#8-状态系统重构方案-IsPermanent合并+DecayMode枚举+事件触发.md` 实施：1) `StateDecayTiming` 枚举加 `Never` / `OnAttackPlayed` / `OnDamaged`；2) `StateDefinition` 删 `IsPermanent` 加 `DecayMode` / `StacksToRemove`" |

### 适用范围
- 写规范 / 文档 / 评论 / 回应时
- 列任务清单 / 状态表时
- 引用其他章节 / 之前对话时

**核心**：**任何脱离上下文的引用都是反人类的**——必须让阅读者**不需要**回到原始上下文也能看懂。
