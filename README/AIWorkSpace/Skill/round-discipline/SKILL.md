# 轮次纪律

> 任务开始前先看这份。项目里最贵的不是单步耗时，而是**往返次数**与**试错次数**：一次「起游戏 + 等就绪」= 分钟级，一次 `dotnet test` = 0.2 秒。

## 一、先量数，再归因

2026-10-03 实测（图形版本机、同一份二进制）：

| 层 | 实测耗时 | 说明 |
|---|---|---|
| `dotnet build 卡牌模拟器.csproj` | ≈ 3.5 s | 不贵，别为省它牺牲正确性 |
| `dotnet test Tests\卡牌模拟器.Tests.csproj`（342 例） | ≈ 0.2 s | 不贵，能跑就跑 |
| 整套 `--run-flow-ui-smoke` | ≈ 14.4 s | **也不贵**（文档旧写的「数分钟」是错的） |
| 单段 `--run-flow-ui-smoke=<段名>` | ≈ 6.0 s | 2026-10-03 新增档位 |
| 一次「起游戏 + 等到接口可用」 | 分钟级 | **大头**：每次重启都要重付 |

**结论**：慢在轮次与试错，不在单步。觉得「这改动怎么这么慢」时，先把各层耗时量出来再下结论，不要凭感觉说是某一层慢。

## 二、一次往返干多件事

- 读文件用 `read_files`（可一次多文件、可带行区间），**并行发**多个工具调用；不要用 `Get-Content` 一条条切片读。
- 一条命令里可以串多个**只读**检查（列目录 + 统计 + grep），中间用 `;`；不要把一条命令当成一次往返的来源。
- 拿不准事实就先查（读文档 / grep / `hil__search_project_memory`），不要猜完再改。

## 三、失败先隔离，再全量

| 顺序 | 做什么 | 为什么 |
|---|---|---|
| ① | 用单测 `--filter` / 单段烟测只跑受影响的那一块 | 把失败点框住，日志只有几十行 |
| ② | 定位并修完 | —— |
| ③ | 收尾 / 提交前再跑全量（build + test + 整套烟测） | 全量是**门**，不是定位工具 |

反例：一次断言失败就重跑整套烟测 —— 跑 4 次 × 15 s 本身不痛，痛的是每次都要翻整条流程日志才知道挂在哪段。

## 四、否定结论必须真递归复核

「没有调用点 / 功能没接线 / 没写断言」这类结论，必须先用**递归** grep 复核后才能说：
`Select-String -Path 'Scripts\**\*.cs'` **不递归**（只查一层目录），会漏掉 `Scripts/Battlefield/Presentation/*.cs` 这类两级路径。命令模板见 [代码检索](../code-search/SKILL.md)。

## 五、长会话任务要一次编排好

- 起一次 Godot（做 API 点打 / 图形烟测）之前，先把**这一轮要验证的步骤全列出来**，一次会话跑完；中途重试 = 重新付分钟级启动成本。
- 需要重试时先问「是脚本写法的问题，还是被测代码的问题」；脚本写法的问题应当先照抄现成脚手架（[局内API点打](../in-run-api-poking/SKILL.md) §二），而不是换一种调用方式重来。

## 六、收尾把工具事实落档

每轮结束时，把新查实的**工具能力边界 / 坑 / 命令**补进本目录对应 skill，或写进项目记忆（`hil__record_project_memory`）。下一轮不必再试错一遍 —— 本目录就是为此存在的。
