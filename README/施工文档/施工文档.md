我先按你当前代码结构拆一下落点。状态定义和状态规则主要在 StateDefinition.cs、LoadStateCsv.cs、StateSystem.cs。卡牌关键词、效果枚举和卡牌运行时实例主要在 CardEnum.cs 和 Card.cs。战斗过程和牌堆流转主要在 BattleSytem.cs。角色实例和牌堆字段在 Character.cs。默认卡组加载在 LoadingSystem.cs。

**逐项思路**
2. 通用State.csv新增“是否弱化效果 / 是否强化弱化效果”
- 现状里 `StateDefinition` 只有 `IsStackable / IsPermanent / TurnStartDecayAmount`，扩展点是对的。
- 但从建模上，我不建议真的长期保留两个布尔值。因为会出现非法组合：
  - 不是弱化效果，但却是强化弱化效果
  - 是弱化效果，但强化字段为空时语义不清
- 更稳的做法是：
  - CSV 层可以先加两列，兼容你的表格习惯。
  - 运行时在 `StateDefinition` 里落成一个单一语义字段，例如 `StateAffinity` 或 `StateKind`：
    - `None`
    - `DebuffNormal`
    - `DebuffEnhanced`
    - `Buff`
- 如果你坚持按文档保留两列，也建议在解析时做约束：
  - `IsEnhancedDebuff=true` 时自动要求 `IsDebuff=true`
  - `IsDebuff=false` 时 `IsEnhancedDebuff` 强制视为 `false`
- 这部分主要改 StateDefinition.cs、LoadStateCsv.cs、CSV 表头。

3. 效果：解除状态栏的第一个普通弱化状态
- 这个需求的关键不是“删状态”，而是“第一个”怎么定义。
- 你现在 `unit.States` 是 `Dictionary<StateType, StateRuntimeData>`，本身没有稳定“第一个”语义。也就是说，当前架构里“状态栏顺序”和“状态数据存储顺序”是脱钩的。
- 所以根上要先补一个“状态显示顺序”的来源。建议两种方案选一种：
  - 方案 A：单位上维护 `List<StateType> StateDisplayOrder`
  - 方案 B：在 `StateRuntimeData` 增加 `AppliedOrder / FirstAppliedFrame / FirstAppliedSequence`
- 然后“解除第一个普通弱化状态”的逻辑就变成：
  - 按状态栏显示顺序遍历
  - 找到第一个 `DebuffNormal`
  - 调用 `StateSystem.RemoveState`
- 这里建议新增一个独立效果类型，不要复用现有 `ClearState`，因为现有 `ClearState` 是按具体 `StateType` 清除，不是按筛选规则清除。
- 比较合理的是新增：
  - `EffectType.ClearFirstNormalDebuff`
- 主要改 CardEnum.cs、Card.cs、StateSystem.cs。
- 风险点只有一个：如果你不先定义“状态栏顺序”，这个效果会变成不稳定行为。

4. 关键词：消耗
- 这是现在牌堆模型里缺的一层。当前角色只有：
  - `handcards`
  - `drawpile`
  - `discardpile`
  - `StatePile`
- 没有 `ExhaustPile`。
- 所以要从根上补一层：
  - 在 `CharacterInstance` 增加 `exhaustPile`
  - 如果你希望怪物或其他单位未来也支持，`IUnitInstance` 也可以补 `ExhaustPile`
- 出牌后的流转逻辑要改在 BattleSytem.cs：
  - 普通牌：仍进弃牌堆
  - `Retain`：只影响回合结束弃牌
  - `Exhaust`：打出后进消耗牌堆
- 这里有一个必须先定的交互问题：
  - 状态牌如果带“消耗”，是“打出时立即进消耗牌堆”，还是“状态结束后进消耗牌堆”？
- 按你文档“打出后移动到消耗牌堆，不再参与抽牌堆、弃牌堆和角色状态牌堆的循环”，更像是“最终归宿是消耗牌堆”，但对状态牌不能立即移走，否则状态牌堆就挂不住这张牌。
- 所以我建议规则定成：
  - 非状态牌：打出后直接进 `ExhaustPile`
  - 状态牌：状态持续期间仍留在目标 `StatePile`，状态结束回收时，如果有 `Exhaust` 则进拥有者 `ExhaustPile`，否则进 `DiscardPile`
- 这样最符合你现在的 `StatePile -> 状态结束回收` 架构。
- 这项需要改：
  - CardEnum.cs
  - Character.cs
  - BattleSytem.cs
  - 可能还要改战斗信息展示 BattleInfoPresenter.cs

5. 状态：勇气铠甲，每打出一张战斗牌，防御1次
- 这项从架构上很好落。
- 关键是先定义“战斗牌”的范围。按你现在 `CardCategory`，我建议：
  - `Attack` 和 `Skill` 算战斗牌
  - `State` 不算
- 然后在出牌成功后统一挂一个状态钩子，而不是在每张牌逻辑里分散处理。
- 最自然的入口就在 BattleSytem.cs 的 `PlayHandCard` 成功结算后：
  - `card.Apply` 成功
  - 扣费、移牌
  - 触发 `StateSystem.OnCardPlayed(sourcePlayer, card)`
- 再由 `StateSystem` 检查：
  - 如果玩家有 `CourageArmor`
  - 且打出的是战斗牌
  - 则触发一次防御
- 这里的“防御1次”也需要先定语义：
  - 如果是“获得1点护盾”，那就是固定 +1
  - 如果是“触发一次防御效果”，那应等于走一遍 ShieldEffect，即 `source.Defend + 0`
- 我更倾向后者，因为你文案写的是“防御1次”而不是“获得1点护盾”。
- 这项主要改：
  - CardEnum.cs
  - StateSystem.cs
  - BattleSytem.cs

6. 关键词：无限升级，记录级数
- 当前 `Card` 运行时实例没有升级字段，所以这项的第一步不是“做效果”，而是先补卡牌升级数据模型。
- 建议直接做通用升级结构，不要只为“无限升级”单独打补丁：
  - `PermanentUpgradeLevel`
  - `BattleUpgradeLevel`
  - `TotalUpgradeLevel => Permanent + Battle`
- 再加一个关键词：
  - `CardKeyWord.InfiniteUpgrade`
- 这样后面第 7、8 项都能复用。
- 但这里还有一个更深的问题：你现在卡牌的数值来自 CSV 固定字段，系统里没有“升级后效果如何变化”的统一公式。
- 所以这项可以先分两阶段：
  - 第一阶段：先把等级记录下来
  - 第二阶段：再定义哪些卡受升级影响、如何把等级映射到伤害/护盾/描述
- 如果不先拆两阶段，后面会很容易陷入“等级记住了，但数值没地方算”的状态。

7. 效果：战斗内升级卡牌
- 这一项技术上可做，但和现有效果框架有一个结构冲突：
  - 你当前 `Card.Apply` 的 effect target 只支持 `IUnitInstance`
  - 升级卡牌的目标其实是“Card”，不是“Unit”
- 所以这类“操作卡牌本身”的效果，不适合继续硬塞进现有 `EffectSystem.ApplyXXX(source, target)` 这条链。
- 更稳的做法是把效果分两类：
  - 单位效果：继续走现在的 `EffectSystem`
  - 卡牌操作效果：由 `BattleSytem` 或单独的 `CardOperationSystem` 处理
- 比如新增效果类型：
  - `UpgradeBattleCard`
- 然后在 `PlayHandCard` 里检测这个效果类型，并按参数解析“要升级哪张卡”：
  - 本张牌自己
  - 手牌某张牌
  - 抽牌堆某张牌
  - 弃牌堆某张牌
- 如果你现在只想做最小闭环，我建议先只支持一种最简单语义：
  - “升级本张牌自身” 或 “升级当前选中的一张手牌”
- 这能避免先引入一套复杂的卡牌目标选择系统。

8. 效果：永久升级卡牌
- 这是这批需求里改动最大的一项，因为它不是战斗内数据，而是“角色卡组资产”的变更。
- 你当前默认卡组来自 LoadingSystem.cs 加载 CSV，战斗开始时再实例化进抽牌堆。
- 这意味着现在没有“角色拥有的、可被永久修改的卡组实体”。CSV 是模板，不应该在战斗里直接改。
- 所以要做这项，必须引入一层新数据：
  - 例如 `CharacterDeckProgress`
  - 里面记录角色当前持有卡牌、每张卡的永久升级等级
- 战斗开始时再根据这层数据实例化：
  - 模板卡牌
  - + 永久升级等级
  - + 本局战斗升级等级初始为 0
- 也就是说，第 8 项不是简单新增一个效果就完事，而是需要补“角色卡组进度模型”。
- 这项我建议单独立一个小里程碑，不要和别的效果混着做。
- 如果你现在还没有存档系统，最小实现也至少要先有一份内存中的 `DeckProgress` 结构，不然“永久升级”没有落点。

9. 效果：攻击，额外造成本局战斗中失去生命值的伤害
- 这项其实比较顺，因为你在 BattleSytem.cs 里已经有 `GetBattleLostHp(IUnitInstance unit)`。
- 也就是说，“本局失去生命值点数”你已经有基础能力了。
- 这里主要要定清楚“取谁的失去生命值”：
  - 攻击者自己本局失去的生命值
  - 还是目标本局失去的生命值
- 文案直觉更像“自己越残血越强”，也就是取 `source`
- 实现上最简单的方式是新增一个效果类型：
  - `DamageByBattleLostHp`
- 或者把它作为 `Damage` 的一种伤害修正参数。
- 我更建议新增独立效果类型，原因是：
  - CSV 更直观
  - 日志更清楚
  - 不会把 `Damage` 的参数语义搞乱
- 然后内部就是：
  - `bonus = BattleSytem.Current.GetBattleLostHp(source)`
  - 再走一次攻击结算

10. 战斗局内记录每个玩家对应的失去生命次数
- 这一项建议不要散落在 `HP` 属性 setter 里硬算，否则以后直接改 HP 的地方一多，语义会失控。
- 你现在已经有：
  - “失去生命点数快照”通过 `BattleInitialHpSnapshots` 计算
- 但“失去生命次数”是事件型统计，需要单独存。
- 推荐在 BattleSytem.cs 里新增：
  - `Dictionary<int, int> BattleHpLossEventCounts`
- 然后在真正造成 HP 下降的统一入口里调用：
  - 比如 `EffectSystem.AttackEffect` 中，当 `hpDamage > 0` 时
  - `BattleSytem.Current.RecordHpLossEvent(target, hpDamage)`
- 但从根上讲，未来如果还有“自残”“毒”“燃烧”“直接扣血”之类效果，这种统计最好不要只埋在 `AttackEffect`。
- 更稳的长期方案是引入统一的 HP 变更入口，例如：
  - `BattleSytem.ApplyHpLoss(target, amount, source, reason)`
- 所有掉血都走它，这样第 9 和第 10 项就都不会漏记。
