# 现状总结与下一步方案（2026-08-28）

本文档记录当前项目（卡牌模拟器 / Godot 4.6 + C#）的整体现状、已识别的关键问题，并按推荐顺序给出下一阶段的改善方案，作为后续施工的基线。

## 一、项目现状

### 1.1 项目类型与引擎

- 引擎：Godot 4.6（Forward Plus）+ C#（.NET 8）
- 类型：卡牌战斗模拟器（类 Slay the Spire / Slay-like 风格）
- 主场景：`Scenes/Battle/CardBattleScene.tscn`
- 启动场景：项目启动后直接进入 `CardBattleScene`，战斗开始前弹出 `BattleSetupWindow`

### 1.2 场景与 UI 体系

| 场景 | 用途 | 备注 |
|------|------|------|
| `Scenes/Battle/CardBattleScene.tscn` | 战斗主场景 | 左侧 3 角色 / 中央日志 / 右侧怪物 / 下方手牌 |
| `Scenes/UI/BattleSetupWindow.tscn` | 战前初始化窗口 | 复用旧 DebugBattle 的角色/怪物/卡牌配置 |
| `Scenes/UI/BattleDebugPanelWindow.tscn` | 调试操作面板 | 仅迁移旧 DebugBattle 的"操作面板"按钮 |
| `Scenes/Debug/DebugBattle.tscn` | 旧调试场景 | 保留兼容，新主场景下不再作为 UI 使用 |
| `Scenes/Card/CardDisplayPrefab.tscn` | 卡牌显示预制体 | 文字已统一调整为黑色 |
| `Scenes/UI/UnitInstanceView.tscn` | 单位视图预制体 | 含血条、护盾、意图、状态图标 |

### 1.3 核心模块

| 模块 | 路径 | 体量 | 职责 |
|------|------|------|------|

| 单位视图 | `Scripts/UI/UnitInstanceView.cs` | ~17 KB | 单个单位的视图绑定 |

### 1.4 已实现功能

#### 战斗系统

- 玩家回合 / 怪物回合交替循环
- 多角色战斗：最多 3 名玩家同时参战，共享行动窗口，可自由切换操控
- 回合开始：状态结算 → 护盾清零 → 抽牌 → 能量重置
- 回合结束：弃置非保留手牌
- 怪物回合：逐只异步执行意图，结束 0.5s 后进入下一只
- 胜负判定：所有怪物死亡 = 胜利；所有玩家死亡 = 失败
- 怪物意图系统：含随机单目标 / 共享随机目标两种多段模式

#### 牌堆体系

- 抽牌堆 / 弃牌堆 / 消耗牌堆 三套独立牌堆
- 抽牌堆为空时自动将弃牌堆洗回
- 状态牌独立牌堆机制：状态牌进入目标 `StatePile`，状态结束回收时根据关键词决定去 `DiscardPile` 或 `ExhaustPile`

#### 效果系统（EffectType）

`None / Damage / Shield / AddState / ClearState / Heal / DrawCard / AddCost / ClearAllStates / ClearFirstNormalDebuff / ShieldSlam / UpgradeBattleCard / UpgradePermanentCard / DamageByBattleLostHp / AddKeyword / MirrorShieldToAllies`

共 16 个效果类型。

#### 状态系统（StateType）

`Vulnerable / Weak / Ignite / CounterAttack / WhirlwindSlash / AddAttack / ExtraEnergy(已废弃) / Void / CourageArmor / TurnStartEffect / GainAttackOnHpLoss / CounterAttackWhenAttacking / ShieldGuard / ShieldCapEqualsHP / ForcedTaunt / RetainAllBattleCards / HpLossPerCardPlayed / BattleCardBlocked / DrawLock / NextBattleCardFree`

共 20 个状态类型。

#### 关键词体系（CardKeyWord）

`None / Retain / Exhaust / InfiniteUpgrade / Crit` + 运行时关键词生命周期 `KeywordFlag`（RemoveAfterActivate / RemoveAtTurnEnd）。

#### 升级系统

- 最小闭环已实现：战斗内升级 + 永久升级
- 卡牌目标选择挂起流程：手牌定向 / 手牌随机 / 默认卡组随机
- 无限升级伤害公式：`基础额外伤害 * 1.2^总级数`，向下取整
- 卡牌 `PermanentUpgradeLevel / BattleUpgradeLevel / TotalUpgradeLevel` 三级记录

#### 卡牌配置

- 重剑手 CSV：`DataBase/Card/重剑手Card.csv` 共 27 张
- 通用 CSV：`DataBase/Card/通用/通用Card.csv`
- 状态配置：`DataBase/State/通用State.csv`（含 `IsDebuff / IsElite` 等扩展字段）

### 1.5 编译状态

- `dotnet build`：0 警告 / 0 错误 ✅

## 二、关键问题清单

### 2.1 代码规模问题

- `BattleSytem.cs` 单文件约 103 KB / ~2900 行，**单文件巨型已严重妨碍迭代**
- `Card.cs` ~33 KB、`CardBattleScene.cs` ~32 KB 也偏大
- `EffectType` / `StateType` 显式指定部分枚举值（14 / 15 等），与按顺序插入的混用，存在维护风险

### 2.2 施工文档未完成事项

来自 `README/施工文档/施工文档.md` 的"待施工事项"：

1. 调试面板中的"结束游戏"按钮需点击后结束本局并回到战前配置界面
2. 调试面板应覆盖战斗场景中的所有节点，当前可能被部分卡牌遮罩
3. 当敌人过多时网格会被拉得太长，导致游戏 UI 无法完整显示，需缩小角色 / 怪物单位

### 2.3 重剑手设计卡未实现

`README/角色设计/卡牌表格/重剑手.csv` 共 30 张设计卡，`DataBase/Card/重剑手Card.csv` 已实现 27 张，**仍有 5 张未实现**：

| 阵地 | 战斗牌 → 已改 State | `ShieldCapEqualsHP=14` 枚举已落 | 需 `StateSystem.OnTurnStart` 新增 ShieldCap 处理 |
| 死亡之舞 | 战斗牌 A 级 | 未实现 | 需运行时修改 `EnergyCost`（架构级改动） |

- Demo 完整功能未实现：地图、完整怪物体系、装备、材料、事件、美术、多角色卡牌设计、完整战斗关卡

## 三、下一步改善方案

按推荐优先级排序，每条标注预期工作量与依赖。

### 3.1 P0 — 优先解决（建议 1~2 个迭代内完成）

#### 方案 A：拆分 BattleSytem.cs（高 ROI）

- 目标：把 ~2900 行的单文件拆成多个职责清晰的子模块
- 建议拆分：
  - `BattleSytem.cs`：仅做主控与单例入口（~500 行）
  - `BattleFlowController.cs`：回合开始 / 结束、抽牌、出牌、怪物回合流程
  - `BattleInfoPresenter.cs`：日志、Tab、状态显示（已有雏形，可下沉）
  - `BattleUiBridge.cs`：与 `CardBattleScene` 之间的 UI 桥接
  - `CardOperationController.cs`：卡牌目标选择挂起 / 选牌上下文
- 预期工作量：3~5 天
- 收益：每次修改只在对应文件定位，单文件 100KB 降到 20~30KB 级别

#### 方案 B：收尾施工文档"待施工事项"

- 结束游戏按钮：`EndGame` 后切回 `BattleSetupWindow`
- 调试面板层级：用 `Layer` 或 `TopLevel=true` 置顶，避免被卡牌遮罩
- 多人战斗 UI：`UnitInstanceView` 缩放或 `GridContainer` columns 自适应
- 预期工作量：1~2 天
- 收益：直接关闭施工文档中长期遗留的体验问题

#### 方案 C：重剑手剩余 5 张卡实现路径

- 推荐先做：阵地 + 城墙 + 到我身后（共用怪物目标选择改造）
- 再做：死亡之舞（需要 `RuntimeEnergyCost` 新机制）
- 最后做：蓄势待发（需要重写出牌流程 + 反击时出牌替代）
- 预期工作量：阵地 1 天 / 城墙+到我身后 2 天 / 死亡之舞 3~5 天 / 蓄势待发 5~7 天
- 收益：补齐重剑手设计表 100% 卡牌
